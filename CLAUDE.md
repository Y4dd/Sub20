# Sub20

A desktop app for getting clips onto Discord: drop videos, trim each with two handles, pick a size, compress. Every result comes out under the size limit, by default well under 20 MB, hence the name.

It exists because the owner was forever cutting clips and re-encoding them by hand to fit Discord's upload limit. Sub20 does both in one place: trim, then a GPU encode aimed at a size, checked after encoding and redone if it lands over.

Sub20 is a Tauri 2 desktop app with a Rust engine driving FFmpeg, free and open source under MIT (`LICENSE`).

**Licence and credit.** Sub20 was inspired by 8mb.local, and the README says so in one line at the end of its Licence section. That line is the only mention, by the owner's decision: don't add others, and don't describe Sub20 as following or deriving from another project. Licensing was settled in November 2026. What Sub20 shares with that project is functional only: bitrate arithmetic, resolution and bitrate ladders, FFmpeg flags, encoder option names, file extensions. Ideas, formulas and settings aren't copyrightable. An 8-word overlap check of both codebases found no shared prose or code, so no permission was needed. Write new code and wording from scratch, not from another project's source.

The owner's brief, which every change should still serve: written in Rust; a step to go through one or more videos and trim them with left/right handles before compressing; a modern, simple interface with fewer buttons. Chosen along the way: native desktop app, no login.

## Layers

Dependencies point one way: `crates/core` ← `src-tauri` ← `src`.

- **`crates/core` (the engine, crate `sub20-core`)** has no GUI code and holds all behaviour. It speaks to the outside through one trait, `EventSink`. Put logic here and test it here. Everything that runs FFmpeg or touches the system sits behind the default `engine` feature (tokio, uuid, trash, sha2); without it the crate is the planner and its types (`plan`, `job`, `probe::MediaInfo`, `settings`, `encoders`, `command`), which build for WebAssembly. Keep new pure logic out of the gated modules so Lite can share it.
- **`crates/plan-wasm` (crate `sub20-plan-wasm`)** exports the planner to the browser as plain functions over memory, JSON in and out (`alloc`, `dealloc`, `plan`, `lower_bitrate`, `size_retries`), so no binding generator is needed. `node scripts/build-plan-wasm.mjs` builds it into `src/lib/web/plan.wasm` (not committed; needs `rustup target add wasm32-unknown-unknown`), and `src/lib/web/planner.ts` loads it. CI tests the core without the engine and builds the WebAssembly.
- **`src-tauri` (the shell, crate `sub20`, lib `sub20_lib`)** is thin: Tauri commands, event forwarding, file access. One command per `Backend` method.
- **`src` (the window)** is Svelte 5 with runes. It reaches the app only through the `Backend` interface in `src/lib/types.ts`, which has three implementations: `tauri.ts` (the desktop app), `web/backend.ts` (Sub20 Lite, in the browser) and `mock.ts` (invented clips and simulated encodes for design work). `Backend::can` says what an implementation offers, and the window hides the rest.

Adding a capability touches, in order: a core function with a test → a command in `src-tauri/src/lib.rs`, registered in `generate_handler!` → a `Backend` method in `types.ts` → `tauri.ts` and `mock.ts`, and `web/backend.ts` or a `can` flag that hides it there → the UI.

`types.ts` mirrors the Rust serde output by hand (camelCase fields, lowercase or camelCase enum variants, `JobEvent` tagged by `type`). Change the Rust type and its mirror in the same edit.

## Commands worth knowing

- `npm run dev` runs the window in a browser on the mock backend. Use it for design work. `?lite` runs Lite instead (it needs `plan.wasm` built).
- `npm run build:web` builds the planner's WebAssembly and Sub20 Lite into `dist-web/` (relative paths, so it can be served from any folder). `npx vite preview --mode web` serves it.
- `npm run tauri dev` runs the real app. A plain `cargo build` debug binary also loads `http://localhost:1420`, so it needs the Vite server.
- `npx tauri build --debug --no-bundle` builds the way a release does (UI embedded, CSP enforced). Run this after touching `tauri.conf.json`, the CSP, or anything loaded by URL.
- `cargo test --workspace`: `crates/core/tests/e2e.rs` runs real FFmpeg encodes and skips itself when FFmpeg is missing.
- `cargo run -p sub20-core --example compress -- [--mb 20] [--encoder NAME] [--out DIR] FILE...` compresses real clips with the app's engine and prints size, encoder and attempts. History stays off.
- Before finishing: `cargo fmt --all`, `cargo clippy --workspace --all-targets`, `npx svelte-check`. All three are clean today; keep them clean.
- The repo lives in a OneDrive folder on the owner's machine. Point `CARGO_TARGET_DIR` outside it so build output is not synced.
- CI (`.github/workflows/ci.yml`) skips commits that change only prose (`*.md`, `docs/`, licences). It runs fmt, `clippy -D warnings` and the tests on Windows and Ubuntu with FFmpeg installed, plus `svelte-check`, the build, `npm audit --omit=dev` and `cargo deny check advisories`. `deny.toml` fails "unmaintained" only for direct dependencies; the ones inside Tauri's tree (zbus, proc-macro-error) are Tauri's.
- `npm run set-version -- x.y.z` writes the version into `package.json`, `tauri.conf.json` and the workspace `Cargo.toml`, and refreshes both lock files.
- `/lite-lab.html` under `npm run dev` is the Sub20 Lite size test: it encodes chosen files with WebCodecs through `src/lib/web/fit.ts` and reports how close each lands to the limit. Dev only; neither build includes it. `lab.run(files)` runs it from a script.

## Engine decisions

**The limit is strict.** A result one byte over the target is encoded again at a lower bitrate (`lower_bitrate`), up to `SIZE_RETRIES` times. An over-limit file is never saved: `when_over` decides between another retry, a switch to the CPU encoder (hardware encoders only, with fresh retries from the planned bitrate), or an `OverLimit` error that names the fix. A hardware retry that shrinks the file by less than 5% means the encoder is at its floor, and the job moves to the CPU at once. Measured on an RTX 5070 Ti: `h264_nvenc` will not go under about 600 kbps on a busy 720p30 clip whatever the flags (691 kbps even at QP 51) and drifts 6–9% over larger targets (17% on a short clip from the owner's NVIDIA folder; the retry fixed it); `hevc_nvenc` and `av1_nvenc` hit low targets. Because nothing over is ever saved, the default sizes can be round (no 9.7 MB to leave room). 1 MB is 1024 × 1024 bytes. `KBIT_PER_MB = 8192` (size in MiB × 8192 = kilobits) leaves about 2.3% for container overhead.

**Planning is pure** (`plan.rs`), so the window calls it on every handle drag.
- Audio yields on tight budgets: at most 34% of the total, stepped down to a floor (Opus 24, AAC 48 kbps). If video would get under 24 kbps the plan is refused with advice, since the result could not fit; the advice says how long a clip the size holds ("20 MB is too small for 2 hours of video: it holds 37 minutes at most"), rounded down, with lengths in words from `timecode::spoken`.
- Automatic resolution picks the size whose result will look best, judged by `rate`: weighted kbps per megapixel (`density`: codec efficiency, frame rate) with 550 good and 220 rough, and a cap for pictures shrunk below 720p (soft) or 480p (rough). Good counts as good enough, ties go to the larger picture (to the smaller when all are rough), and the size is chosen with the same rounded kbps the verdict is given with. Choice and verdict share one measure, so a shorter trim never looks worse (`shorter_trims_never_look_worse`). This replaced a rule that preferred 1080p and judged by raw kbps, which turned "720p, good" into "1080p, soft" when a clip was trimmed shorter. Portrait behaves like landscape; the source size is a candidate too. `plan_within` takes the largest short side the encoder takes and chooses among the sizes at or under it (Lite's GPU limit); `plan` is it with no limit.
- The scale filter gets explicit even `W:H`, computed in the planner from display dimensions (rotation applied).
- A trim that keeps the whole video is treated as no trim.

**Trim** is `-ss` before `-i` and `-t` after it. Everything is re-encoded, so the cut is exact.

**Cutting a result** (`cut.rs`, `Engine::cut_result`) shortens a finished file without encoding it again, by the owner's choice over compressing again from the source (November 2026, after beta testers trimmed results they had already compressed). The packets are copied (`-c copy -map 0`), so it is quick, loses nothing and only gets smaller. A copy has to begin on a keyframe, but in MP4 and MOV (`cut::starts_anywhere`) the start stays where the handle is: the seek is the start itself, the packets from the keyframe before are kept, and the muxer's edit list starts playback at the start (checked in Chromium, November 2026: the first frame matched the source's exactly; Discord's desktop player and Sub20's window are Chromium). `Engine::keyframes` lists none for them, so the window has nothing to snap to. Matroska has no edit list: there the start moves back to the keyframe at or before it (`snap_start`, mirrored by `snapStart` in `app.svelte.ts`; change them together), and the seek lands half a second past it, because Matroska's seek goes back by the B-frame delay first (1 ms past it landed on the keyframe before). The end lands within a few frames (B-frames). No `-avoid_negative_ts make_zero`: with B-frames it pushed the video's start to 0.07 s and stretched the file. Every encode sets `-g` to two seconds at the output frame rate (`command::KEYFRAME_SECONDS`), against the encoders' 250 frames (8 s at 30 fps); NVENC's H.264, HEVC and AV1 all honour it, and it helps Discord's player seek. The cut takes the result's name through `output::place`, the uncut file goes to the bin (both stay if the bin refuses), and the history entry follows (`History::cut`). The window moves the original's trim by the snapped start, so Compress again starts from what is kept.

**Encoders.** The user picks a codec; `Report::best` picks the encoder, hardware first. `options.encoder` overrides. Detection encodes two real frames per encoder, because FFmpeg lists encoders whose GPU is absent; families run side by side, encoders within a family take turns (consumer GPUs cap sessions). A hardware failure mid-job falls back to the CPU encoder for that codec, ignoring the user's disabled list so the job finishes. `libaom-av1` is never automatic.

**Effort `Max`** keeps the size target: slowest preset everywhere, plus two passes on libx264 and libx265 only. Pass statistics use the encoder's default file names in the working directory, so each job runs FFmpeg from its own scratch folder; that avoids escaping Windows paths inside `-x265-params`. It never switches to constant quality, which would ignore the size.

**Hardware decode** is `-hwaccel auto` with frames returned to system memory, so the software filter chain is unchanged; on failure the job retries with CPU decoding.

**HDR** (PQ or HLG, read from `color_transfer` into `MediaInfo::hdr`) is tone-mapped to SDR first in the filter chain (`command::TONE_MAP`: `zscale` to linear, `tonemap` Mobius, back to BT.709), encoded 8-bit and tagged BT.709. Untreated, HDR came out grey (saturation 23 against the SDR original's 114 on a generated PQ clip); Mobius kept the most colour (87, against Reinhard 81 and Hable 64). It needs FFmpeg with zscale (`Report::tone_map`, from `ffmpeg -filters`); without it the job runs untreated, logs why, and the stage warns. Audio-only jobs skip it.

**Stream mapping** is `0:V:0` (skips cover art), the sound, `-sn -dn`. Opus in MP4 becomes AAC. HEVC in MP4 gets `-tag:v hvc1`.

**Several audio tracks are mixed** (`EncodeOptions::mix_audio`, on by default), because OBS and the NVIDIA app can record the microphone on a track of its own and keeping only the first lost it. `command::audio_input` makes each track stereo (`aformat`; a mono mic lands in the middle), sums them with `amix normalize=0` (the default divides each input by the track count, so the game came out quieter), and puts `alimiter` after it for the peaks the sum pushes over. One track, or mixing off, maps `0:a:0?` as before. `MediaInfo::audio_tracks` counts them; the other audio facts describe track 1. The e2e test makes a silent "game" track and a tone "mic" track and checks the mic is heard at full volume.

**Output.** FFmpeg writes `.{stem}.{id}.part.{ext}` in the destination folder; a `Cleanup` guard removes the partial file and scratch folder on every exit path. `output::place` moves it to its final name: a name the user typed (`JobSpec::output_name`, cleaned by `output::clean_name` for every system), else `stem-20mb.ext`, `stem-2500k.ext` or `stem-audio.ext`. `looks_generated` recognises the default names so the folder watch skips its own output: change the naming and that function together. A typed name is not recognised, so a manual result saved into a watched folder would be picked up.

**Replace the original** (`OutputMode::Replace`, sent as `JobSpec::replace_original`) saves the result under a free name first, then moves the original to the bin (`trash` crate, injected as a closure so tests use a fake bin), and only then renames the result to the wanted name; if the bin refuses, both stay and the job logs why. `JobResult::replaced_original` tells the window, which then hides Original, Compress again and the trim, since the source is gone. Manual jobs only: the watch treats Replace as `SameFolder` and `tidy()` resets a watch set to it. `Engine::rename_result` renames a finished file and retargets its history entry.

**Queue.** A job takes its place in line synchronously in `Engine::start`, before its task is spawned; spawn order is not run order on a multi-thread runtime, and that was a real bug. Automatic parallelism is `cores / 8`, clamped 1–3.

**Stopping FFmpeg** goes through `ffmpeg::kill_tree`. On Windows `ffmpeg.exe` may be a launcher (Chocolatey's ShimGen shims start the real FFmpeg as a child), and killing the launcher alone leaves FFmpeg running and writing; `taskkill /T /F` on the launcher's PID stops both. Timed-out helper runs do the same. Found on CI, where Chocolatey installs FFmpeg; Scoop's shims pass the kill on.

**Failures name the cause and the fix.** `advice::explain` rewrites a failed job's error before the `Failed` event: the source moved or deleted (checked first, since it explains what follows), the results folder gone, a full disk (FFmpeg's words or the OS error code), a folder Sub20 may not write to versus a source it may not read (FFmpeg names the `.part.` file when it is the output), and a source that can't be read as a video, which also covers a recording still being written. Anything else keeps FFmpeg's telling line. Add a case there, with a unit test, rather than rewording errors where they are raised.

**Progress** comes from `-progress pipe:1`; stderr is the log. `percent` is per attempt and restarts on `Retry`; two-pass splits it 0–50 and 50–100.

**Folder watch polls** on a timer by design: it behaves the same on network shares and synced folders, and "stopped changing for N seconds" answers "has the copy finished?". Its memory (`watch.json`) is keyed by path plus size and mtime; a file whose directory listing still shows the handled size and mtime is skipped without being opened (on Windows reading them from the file means opening it: 2,000 files cost 2.6% of a core before), and anything else is asked of the file itself, because NTFS may not update the listing while a recording is still being written; the "already there" baseline is taken once per folder. `watch::clip_folders` finds the NVIDIA app's (`VideosNVIDIA`, a folder per game) and Xbox Game Bar's (`VideosCaptures`) clip folders on Windows; Settings offers each as a one-click watch, new clips only. Steam is left out: its recordings are stream segments, not video files.

**The watch puts clips on the bench** by default (owner, 20 November 2026, plan 7's 7.12: people trim first). A settled clip is handed to the shell as `Arrival::Bench` through the `Hand` given to `Watcher::new` and marked `benched` in `watch.json`, so it is handed over once; `WatchSettings::compress` ("Compress new videos straight away", off by default and for watches set up before) sends it to the engine instead, as below. Profile, Results and Originals apply only to compressing; the notice toggle shows for the bench only with `keep_watching` on, since the bench is noticed only with no window.

**The watch at launch** (compressing only; the bench takes any number). More than `watch::PILE` new clips on the first scan after launch (or a reload with the folder unchanged) are held, not queued; `WatchStatus::waiting` counts them, the shell is told once (`Arrival::Pile`), and the window asks once (`Watcher::decide`, `watch_decide`); its banner says they arrived "while Sub20 wasn't watching", since a resume holds a pile too. Skipping marks them skipped in `watch.json`, so they are never asked about again. A few new clips go straight in.

**Settings** deserialize with `#[serde(default)]` and pass through `tidy()`, so old or hand-edited files load; `settings::read_json` drops a byte-order mark (Windows PowerShell 5 writes one) for settings, history and the watch memory. A damaged file is renamed to `settings.broken.json`. There is no file retention (no uploaded copies exist); the equivalent is `history_keep_days`. Settings live in the app data folder for the identifier `io.github.y4dd.sub20`.

**FFmpeg lookup order:** the folder in settings, bundled (`resources/ffmpeg`, resources, beside the executable), `PATH`, then usual install folders (Chocolatey, Scoop and winget on Windows). In bundled folders `sub20-ffmpeg`/`sub20-ffprobe` come first: the release ships FFmpeg under those names, because a Linux package puts sidecars in `/usr/bin`, where `ffmpeg` would clash with the distribution's package.

## Shell decisions

- Commands that reach `Engine::submit` or `Watcher::reload` are `async`: both call `tokio::spawn` and need the runtime.
- The asset-protocol scope starts empty. Each added video is allowed at runtime in `add_videos`; the thumbnail cache folder is allowed at startup.
- **The shell trusts the window's paths no more than it must** (plan 3's task 3.9). Sources must be absolute (`local()`; `crawl::find_videos` drops the rest), and every FFmpeg and FFprobe source input gets `command::LOCAL_ONLY` (`-protocol_whitelist file`), since FFmpeg reads `http://…` or `concat:…` as a URL. Folders are chosen through `pick_folder`, a shell-side dialog that remembers them in `AppState::picked`, and `save_settings` refuses a new `ffmpeg_folder` that wasn't picked there, because the FFmpeg found in it runs. Files and other dialogs stay in the window. `open_file` opens only results and FFmpeg's licence notice. `reveal` is left open: it only shows a file, and History shows old entries. The Linux media server lets a connection go if its request head takes over 10 seconds.
- **Linux preview playback** goes through `media.rs`, a loopback HTTP server (127.0.0.1, random port, random token, registered files only, range requests). WebKitGTK hands media to GStreamer, which cannot read the asset protocol. Windows uses the asset protocol. The CSP's `media-src` allows `http://127.0.0.1:*` for this.
- A source the webview cannot decode fires `<video>`'s `onerror`, and the stage switches to still frames from `preview_frame`.
- **Quitting asks** while jobs are queued or running (`may_quit`, on `CloseRequested` and `ExitRequested`, so the custom close button and Alt+F4 both ask): a native dialog, "Stop and quit" or "Keep compressing". On exit the shell cancels all jobs and waits briefly so no FFmpeg child outlives the app. Installing an update stops jobs without asking; its link says so ("Stop compressing, update and restart").
- **The tray** (Windows only, plan 7; `tray.rs`, Tauri's `tray-icon` feature in the Windows-only dependency table, so Linux builds have none): the icon is up while `WatchSettings::keep_watching` and the watch are both on (`follow_tray`, at startup and on every `save_settings`). Then closing the window destroys it and keeps the process (`stays_in_tray`, which also needs the icon to be there, so a process is never left with no way back): `CloseRequested` asks only about manual jobs (`Engine::active_manual`), and `ExitRequested` with no code (the last window closed) is prevented. With an update found, the menu also has Update to x.y.z (Downloading… while it installs); `tray::refresh` builds the menu from `AppState` every time. A left click or Open builds the window again (`show_window`, on a thread of its own, since building one inside an event handler can deadlock WebView2); Quit is `exit(0)`, which asks through `may_quit` about every job. Pause watching (the tray's item, which becomes Resume watching, and History's Pause link; `Watcher::pause`, `set_paused`) stops the scan for this session and lets running jobs finish; settings saves keep the pause, switching the watch off ends it, and resuming counts as a launch, so more than `PILE` clips to compress are asked about. The title bar says "Watch paused" with a ring for its dot. With no window the process is 8–9 MB, with no WebView2 processes.
- **Crashes** are appended to `crash.log` in the app's log folder by a panic hook (`log_crashes`, restarted past 256 KB). **Copy diagnostics** (the about line at the bottom of Settings) puts `sub20_core::diagnostics::report` on the clipboard through `clipboard-rs`: versions, build, system (`os_info`), FFmpeg, the encoder report, the crash log's end and the shown job's FFmpeg log, with the home folder written as `~` so it can be pasted in public. There is no telemetry; the update check is the only request the app makes by itself.
- **Adding videos**: `find_videos` (`sub20_core::crawl`) turns a drop or a choice into files: a folder is searched with its subfolders, its own videos by name before its subfolders, leaving out Sub20's results (`looks_generated`), `.part.` files, hidden entries and links to folders, up to `crawl::MOST` (1,000). The window then reads them six at a time (`ADD_AT_ONCE`, one `add_videos` call per file) and each joins the list once it and every file before it are read, so a big drop fills in name order instead of showing nothing until the last; filmstrips run two at a time (`THUMBS_AT_ONCE`), the selected video's first. Before, a 30-video drop started 30 filmstrips of four FFmpeg processes each. "Or choose a folder of videos" under the empty bracket picks a folder (desktop only).
- **Filmstrips arrive one by one**: `thumbs::filmstrip` reports each frame through a callback, the `filmstrip` command forwards them over a Tauri `Channel`, and the window fills empty places (`""`) in `Clip::thumbs` as they come.
- **Opened videos** (command line, "Open with", Explorer's "Compress with Sub20", a Linux file manager) go through `hand_over`: the startup arguments, and a second launch caught by `tauri-plugin-single-instance` (registered first, so it quits before anything starts). A second launch brings the window forward even with no files, and builds it again if it was closed (`show_window`; plan 7's 7.2). The window isn't made from the config at startup (`create: false` in both window configs): `setup` builds it with `show_window` once the state is managed, the same way it comes back later. Until the window's `bootstrap` takes them they wait in the static `OPENED`; after, they arrive as `opened` events (`WINDOW_READY`, cleared when the window is destroyed, so they wait again for the next one) (`Backend::onOpened`), gathered until none come for 150 ms (`OPENED_QUIET`) and sent as one batch in Explorer's name order (`in_name_order`), because Explorer starts Sub20 once per selected file. Windows registers through NSIS hooks (`src-tauri/windows/hooks.nsh`): `OpenWithProgids` and a `SystemFileAssociations` verb, never the default program, because Tauri's own `fileAssociations` takes over `.mp4`'s default on Windows. Linux declares `fileAssociations` in `tauri.linux.conf.json` (MIME types for the `.desktop` file). Keep the two type lists in step.
- **Two builds**, shown to people as "Sub20" and "Sub20 without FFmpeg" ("lean" is the internal name, kept in the updater keys and `--flavor`). The one without FFmpeg (plain `tauri build`) finds FFmpeg on the system, or downloads it: when none is found, the first screen offers "Download FFmpeg" (`download_ffmpeg`, `sub20_core::fetch`). It fetches the archive pinned in `scripts/ffmpeg.json` (Sub20's own FFmpeg release, below). It is checked against its SHA-256, unpacked with the system's bsdtar, and installed as `sub20-ffmpeg`/`sub20-ffprobe` with its licence in the app's local data folder (`ffmpeg/`), which is one of the bundled folders. HTTP uses the updater's `reqwest` with ring TLS, so no other TLS stack is built. `?noffmpeg` (`=fail`) shows the screen on the mock. The full one adds `tauri.bundled.conf.json`: FFmpeg as `externalBin` sidecars, fetched by `scripts/fetch-ffmpeg.mjs` from the pins in `scripts/ffmpeg.json` (SHA-256 checked), plus its GPL text and origin under `resources/ffmpeg/`. Never run those downloads on the owner's machine; CI fetches them.
- **Sub20 builds its own FFmpeg** (`scripts/ffmpeg-build/`, `.github/workflows/ffmpeg.yml`), so the GPL's corresponding source can ship beside the binaries. `sources.json` pins every source archive with SHA-256 (`sources.mjs pin` fills in new ones; it downloads with curl, because code.videolan.org refuses Node's fetch). `build.sh TARGET OUT` builds only what Sub20 uses: x264, x265 (8-bit), SVT-AV1, dav1d, Opus, zimg, zlib, plus NVENC, AMF and Quick Sync headers and dispatchers on Windows and Linux, Media Foundation on Windows, VAAPI (static libva and libdrm, driver search path set for Debian, Fedora and Arch) on Linux; `--enable-version3`, so GPL 3. Windows is cross-compiled on Ubuntu with mingw-w64 (posix threads); Linux builds on Ubuntu 22.04 with static libstdc++. The scripts and workflow still build macOS (`aarch64-apple-darwin`, published in `ffmpeg-9.0.2-1`); the next revision drops it, so a push doesn't rebuild FFmpeg for nothing before then. The script fails if a binary needs a library outside the system's own. The workflow builds on a push to those files, then `check.mjs` (encoders, decoders, filters, the HDR chain) and the e2e tests under `SUB20_E2E_STRICT` (a test that would skip fails) run on each system. Run by hand with "publish", it makes a pre-release `ffmpeg-<version>-<revision>` (never "latest", which the updater reads) holding the binaries, every source archive, the build scripts and `SHA256SUMS.txt`. Then point `scripts/ffmpeg.json` at the new binaries. Bump `revision` for any change; never delete or replace a published FFmpeg release, because released apps download from it. Measured November 2026: 6–13 minutes per system from scratch; 36 MB (Windows zip) and 25 MB (Linux).
- **Updates** use `tauri-plugin-updater` from Rust (`check_update`, `install_update`), one `latest.json` on the latest GitHub release. Each build asks for its own key, `{os}-{arch}` or `{os}-{arch}-lean`, and on Linux `-deb` or `-rpm` before the `-lean` for those packages, because the updater installs a deb with dpkg and an rpm with rpm and refuses an AppImage there (`update_target`, `update_key`; the package comes from `tauri::utils::platform::bundle_type`, stamped into each package by the bundler; `bundled()` tells the full download by the `sub20-ffmpeg` sidecar beside the program, read at run time so one compile serves both), so an install stays the kind it started as. The window checks at startup when `Settings::check_updates` is on, silently on failure; the shell checks only when it starts without a window. Both go through `find_update`, which keeps the `Update` for `install` (cloned, so a failed install can be tried again; one at a time, `AppState::installing`) and puts **Update to x.y.z** in the tray (plan 7's 7.7). Installing stops running jobs first; from the tray it asks first while any run (`update_from_tray`), and a failure is a notice. The updater relaunches the new version with the old one's startup arguments, which Sub20 can't add to, so an install with no window writes `restart-in-tray` (the old version) in the updater's `on_before_exit`; `back_in_tray` reads and deletes it at start and, when the version differs, the icon is up and no videos were handed over, starts without a window. It works from the first update whose old version has it. The public key is in `tauri.conf.json`; the private key is `~/.tauri/sub20-updater.key` on the owner's machine and the `TAURI_SIGNING_PRIVATE_KEY` secret. Losing it means existing installs can't update.
- **Releases**: a `v*` tag runs `release.yml`: a draft release named from `CHANGELOG.md`, one job per system (Windows x64 NSIS, Linux AppImage/deb/rpm) that compiles once (`tauri build --no-bundle`) and packages twice with `tauri bundle`, lean then full, with `tauri.release.conf.json` (updater artifacts), renamed by `scripts/collect-release.mjs` (`Sub20-without-FFmpeg_*` for lean) into one artifact per download, then `latest.json`, `SHA256SUMS.txt` and the release notes, which the feed job rewrites to open with "Which file do I need?" (a table of the downloads with their sizes, `ROWS` in that script). Run by hand, it builds without releasing. The release cache is saved from `main` only (a tag's cache can't be read by the next tag), so a dry run on `main` shortly before tagging leaves it warm.
- **Code signing for 1.0** (owner, 15 November 2026, reversing "no code signing"): the Windows installer and `sub20.exe` through SignPath Foundation, free for open source, which makes SignPath Foundation the publisher on the certificate (plan 3's task 3.8). Until it is granted, releases are unsigned and Windows shows SmartScreen; the README's Install section and the download page say how, and nothing claims signing before it exists. When it is wired in, Authenticode signing must come before the updater's `.sig`, which covers the installer's bytes. SignPath requires a "Code signing policy" page linked from the home and download pages, and once signing is granted the credit "Free code signing provided by SignPath.io, certificate by SignPath Foundation": that is a required service credit, separate from the one inspiration line in the README, so keep it. Update signing (the updater key) is separate and in place.
- **No macOS desktop app** (owner, 15 November 2026): Sub20 is built for Windows and Linux. 0.9.3 was the last macOS build; its installs keep working and get no updates (the feed has no `darwin` keys, and the window ignores a failed update check). Never delete the published 0.9.x Mac files or the macOS archive in `ffmpeg-9.0.2-1`. Sub20 Lite in Safari, on macOS and iOS, stays, so the window's ⌘ shortcuts and the iOS web-app tags stay too.
- **Watch notices** (`notify.rs`): the sink hands every job event to `Notices::see`, which follows watch jobs (only `Queued` carries `origin`) and shows one notification per finished clip, unless `WatchSettings::notify` is off or Sub20's window has the focus. On Windows it holds them while the user is busy (`SHQueryUserNotificationState`, or another app's window fills the screen, which catches borderless games), rechecking every 10 s, then says what piled up in one notice. Elsewhere the system's Focus and Do Not Disturb decide. With no window (`window_gone`: none, and none being built; the watch's first reload starts after `show_window`, so a pile at an ordinary launch is the window's to ask), it also says when the watch put clips on the bench (`Notices::benched`, "clip.mp4 is on the bench") and when a pile is held (`Notices::pile`, "7 clips arrived while Sub20 wasn't watching"), both held during games and dropped if a window has opened by then (the pile also if it was answered) (plan 7's 7.6). A notice carries what a click opens (`extra("clicked")`, `notify::Clicked`, mirrored as `NoticeClick`: `results`, `bench` or `pile`), and `notify::listen` hears a click through the plugin's `on_action` (2.8 reports clicks on desktop; registered before the first notice, since one shown without a handler reports nothing): the window comes forward (`notice_clicked`; built again if it was closed, and then the click waits in `NOTICE` for `bootstrap`) and hears `notice`, and `openNotice` puts one result on the bench (`openWatched`) or opens History for several or for failures, selects the one benched clip a bench notice names (a rebuilt window does this once the saved bench is back), or shows the pile question. A debug test copy shows notices only from a folder ending in `	argetdebug` (copy the exe to `%LOCALAPPDATA%sub20-test	argetdebug`): elsewhere the plugin sends them under the identifier, which only the installer registers, and Windows drops them silently. On Windows a click counts while the notice is on screen, not from the notification centre, which would need a COM activator and a registered app identity. `?watch=notice` clicks one on the mock, `?watch=bench-notice` and `?watch=pile-notice` the other two.
- **The watch in the window**: `app.watch` is polled every 4 s while a watch is on; the shell keeps this session's watch jobs (`sub20_core::watched::WatchedJobs`, fed by the sink, at most 50) and `bootstrap` returns them, so a window built again lists them; `app.watched` starts from that list and follows the same jobs, built from job events whose `queued` said `origin: "watch"` (they never become clips). The title bar shows a short status; History lists them with Open (`openWatched` puts the source on the bench as a finished clip) and Copy. On the mock, `?watch` puts a demo clip on the bench now and then, `?watch=compress` compresses it instead, and `?watch=pile` (compressing) adds a pile to ask about.
- **The bench is kept** (plan 7's 7.13; `sub20_core::bench`, `bench.json` in the app data folder): the window saves its unfinished clips (path, trim, typed name, "leave out"; running ones too, since quitting stops them) through `save_bench` 400 ms after they change, one save at a time, and not before the saved bench has been put back, which would write over it; its own close button saves first. `bootstrap` returns the file, minus files that are gone, and the window adds those clips first, then what Sub20 was opened with. Clips the watch benches (`bench_arrivals`) are added to the file under the `OPENED` lock, leaving out Sub20's own results, then sent as `benched` events while a window is ready (`Backend::onBenched`; they join without taking the selection), so a clip found while there is no window is there when one opens. Desktop only: Lite and the mock keep nothing.
- **Results** are remembered in `AppState::results` as job `Done` events pass through the sink. `result_url` (preview), `open_file` (the default player) and `copy_file` (clipboard, via `clipboard-rs`; CF_HDROP on Windows) refuse any other path. Drag-out is `tauri-plugin-drag` called from the window, with a filmstrip thumbnail file as the drag image (`tauri.ts` keeps thumbnail URL → file).
- **Window frame** differs by platform: `tauri.windows.conf.json` turns decorations off and the window draws its own buttons (`Frame` "custom"); Linux keeps the native frame ("native"), and so does Lite. The title bar is `data-tauri-drag-region`; the window permissions it needs are listed in `capabilities/default.json`.
- Out of scope by decision: login, the Android app, upload storage.

## Lite decisions

Sub20 Lite is the same window on a third backend, `src/lib/web/backend.ts`: WebCodecs encodes on the browser's own GPU encoder, Mediabunny reads and writes the files, and the planner is `plan.rs` through WebAssembly. Nothing is uploaded.

- **Which backend**: `app.svelte.ts` picks Lite when `VITE_TARGET=web` (`.env.web`, read by `--mode web`) or `?lite` under `npm run dev`. In each build a Vite alias swaps the backend it never uses for `src/lib/absent.ts`, so the desktop bundle carries no Lite code or planner and the web bundle no mock or Tauri code. Check both after touching the imports: `grep` the built assets for `webBackend` and `mockBackend`.
- **Capability flags** (`Capabilities` in `types.ts`; `DESKTOP` for the other two) hide what a browser can't do: Settings keeps Sizes and Profiles, Options drops effort, file type, encoders and the FFmpeg toggles, History and Show in folder go. Copy becomes `app.handOff`: **Download** on a computer, **Share** (`navigator.share` with the file) on a phone or tablet (`pointer: coarse`), which hands it straight to the Discord app.
- **Files** have made-up paths (`lite-N/name`, `result-ID/name.mp4`) mapped to `File`s and result blobs held in memory; the window treats them as paths as before.
- **Planned within the GPU** (`web/gpu.ts`): before planning, Lite asks WebCodecs the largest short side the GPU takes at the clip's frame rate (1440p60 can be refused where 1440p30 is taken; refused, the browser falls to its software encoder, which ignores low bitrates), cached per size and rate, and plans with `plan::plan_within`, so the stage's size and verdict are the encode's. `fit.ts` still steps down if the GPU refuses at encode time.
- **Jobs** run one at a time (one GPU encoder to share), each with an `AbortController` for Cancel. Constant bitrate: 6 of 6 test clips landed under on the first try, against 2 of 6 with variable. Encoder names are `{codec}_browser` (GPU) and `{codec}_browsercpu`.
- **Codecs** (`web/gpu.ts`, `codecsHere`): Lite asks WebCodecs once which of H.264, AV1 and HEVC the browser encodes, reports them as its encoders (so Options offers the ones that work), and encodes the codec picked; where the browser lacks it, the first it has, in the order H.264, AV1, HEVC (Discord's desktop app plays AV1 on any computer; HEVC needs a computer that decodes it), with a log line. Always MP4; sound AAC, else Opus.
- **Several sound tracks are mixed** in Lite too (`web/mix.ts`, November 2026): Mediabunny hands each sample of the first track to `process` as 48 kHz stereo; the other tracks are decoded alongside with `AudioSampleSink`, made stereo, resampled by interpolation, summed, and limited at 0.95 like the desktop. Checked on generated clips: a 44.1 kHz mono mic beside a silent game track came out at full volume, and two loud tracks peaked at 0.95.
- **Mediabunny loads with the first video** (`web/media.ts`, a dynamic import, about 570 kB); the page itself is about 155 kB.
- **Installable**: `scripts/vite-lite.mjs` writes the manifest (share target, file handlers), the icons and `sw.js`, which precaches every built file under a cache named by their hash and keeps shared videos in `sub20-shared` until the page takes them (`?shared`). The worker registers in production builds only. The built-in browser pane can't register service workers; test them in headless Edge over the DevTools protocol.
- **Phone layout** is CSS only: under 720 px the clip list is a strip, the dock wraps, Options stacks its labels at 480 px. The stage clips its overflow there, because the trim handles' grab areas reach past the screen and a phone widens the page to show them.
- **HDR** is converted by drawing each frame into an sRGB canvas (`fit.ts`, `toOrdinaryColour`): the browser converts it, right in hue and about a fifth darker than the desktop's Mobius (saturation 80 against 97 on a 203-nit clip; untreated 25). The decoded frames are opaque GPU frames, so the desktop's curve can't run on their values. Mediabunny's resize draws through a canvas too, so scaled clips were converted all along.
- **Large results on disk** (`web/store.ts`): a limit of 64 MB or more writes the result as it is made into the origin private file system (`StreamTarget`, `fastStart: false`), and it is handed on as a disk-backed `File`; over-limit, canceled and unkept attempts are deleted, and the folder is emptied when Lite opens. Smaller results stay in memory with the index at the front.
- **Not in Lite yet**: VP9 (no place in the codec picker; plan 6), cutting a result (`can.cut`; Mediabunny could copy the packets from a keyframe).

## Interface decisions

The brief was "modern, intuitive, fewer buttons, sleek and simple". How that was answered so far:

- **One screen.** A title bar across the top (wordmark, History, Settings, and on Windows the window buttons), clip list, stage (preview, timeline, the plan or result row), dock (size, options summary, one action or the batch progress). Options, Settings and History are sheets that slide over it.
- **The trim bracket is the signature.** Yellow handles are the convention for the kept range in video editors. The bracket is the empty-state drop target, the timeline control, the app icon (with "20" inside), and the progress display (the kept range fills from the left while encoding). `--trim` is reserved for the bracket, the primary action, the selected-clip marker and switched-on toggles.
- **One primary button.** Everything else is a text link (`.link`) where it applies; the exceptions are the finished clip's file chip (drag it out, click to play) and Copy, because getting the file into Discord is the point. Icons are limited to history, settings, close, remove, rename (pencil), copy, the drag grip and the window buttons.
- **Size and options are global** to the list; **trim is per clip**. Editing a finished clip's trim puts it back to ready. So is leaving a clip out (`Clip::leftOut`, "Leave out" on the stage, `s`, or the clip list's checkbox): it stays on the bench with its trim and name, Compress skips it (`pending` against `compressible`), the dock counts "Compress 1 of 3 videos", and Clear finished leaves it alone. With more than one video (`app.choosing`), each clip that can be compressed has a checkbox (ticked is not left out) and a line above the list ticks or clears them all (`includeAll`), after a tester missed "Leave out" (November 2026). The boxes are drawn in the app's own style over a real hidden input, yellow when ticked like the toggles; rows without one keep its strip so the pictures line up.
- **Copy:** sentence case, plain verbs, commas between facts. The status line says what will happen, is happening, or happened. Errors name the cause and the fix. An action keeps one name everywhere.
- **Getting it into Discord** is the end of every job: the finished state previews the result (Original/Result switch), offers Copy (Ctrl+C) and a file chip to drag out. The result plays in the same player as the original (it had the native `<video controls>`, which testers couldn't seek), over a `Timeline` of its own: the result's filmstrip and handles that set `Clip::cutStart`/`cutEnd`. Moving them shows what Cut keeps, its length, about how big, "Same quality", with **Cut** and **Keep all of it** in place of the file chip. On an MKV result, while the start is dragged, the handle follows the pointer and a mark shows the keyframe it will snap to; it settles there on release (an MP4 has nothing to snap to). `Timeline` takes plain props (duration, start, end, thumbs, `stops` for the keyframes) and an `ontrim`, so one component serves both views, and the stage's keys (`[`, `]`, `0`, `$`) act on whichever is shown. The size picker names the Discord limit each preset matches (`discordTier` in `format.ts`; change it when Discord changes its plans). Presets live in settings as plain numbers: Discord's tiers, 20, 50, 500 and 1024 (`DISCORD_SIZES`), default 20 MB (`DEFAULT_TARGET_MB`). A saved list still equal to the old default (20, 50, 100, 500) moves to the new one in `tidy()`; an edited list is left alone. Whole gigabytes show as GB (`sizeParts`, `sizeName`). The picker names them Free, Nitro Basic, Server boost and Nitro (owner, November 2026). Options lists all three codecs with where each plays in Discord (`CODECS` in `OptionsSheet.svelte`), and the dock summary adds a caveat after HEVC and AV1: "may not play on every device", "may not play on phones".
- **The last options** are saved to `Settings::last_options` a second after they stop changing and restored at launch, with the matching profile name when they equal one. `saveSettings` in the window runs one save at a time so two quick changes can't overwrite each other.
- **Progress moves by transform** (`scaleX`, `translateX`), never width or left: progress events arrive twice a second and a width transition lays the page out every frame (WebView2 used 55% of a core during a compress; 33% after).
- **Tokens** live in `src/app.css`. Dark by default, light through `prefers-color-scheme`. Yellow on the light background is only 1.35:1, so marks drawn in yellow use `--trim-mark` and yellow shapes get a `--trim-edge` outline (both a deep amber in light, plain yellow / nothing in dark). Fonts are bundled (the app works offline): Bricolage Grotesque for display, condensed with `font-stretch`, and Hanken Grotesk for the interface, with tabular figures. Monospace appears only in the FFmpeg log. Corner radii differ by role.
- **Icon source** is `public/icon.svg`. Regenerate the app icons with `npx tauri icon public/icon.svg`, then delete the `android` and `ios` folders it creates.
- **State** lives in `src/lib/app.svelte.ts`. `Clip` is a class with `$state` fields. Job events can arrive before `compress()` returns its ids, hence the `#early` buffer.
- **Accessibility.** Text is at least 4.5:1 against its background in both schemes, so `--faint` is for marks and struck-through choices, not for words that carry meaning (a disabled toggle keeps `--muted` text and dims its switch). Sheets are modal: Tab stays inside, Escape closes, focus returns to the opener. `Segmented` is a radio group with one tab stop and arrow keys. Icon-only buttons carry `aria-label`.
- **Keyboard** handling is in `App.svelte`: arrow keys and vim motions in one interpreter (`vim()`), with counts and two-key commands (`gg`, `dd`, `cw`) that wait a second for their second key. Plain letters are safe because the handler ignores keys typed into fields and keys while a sheet is open. `?` opens `KeysSheet`; keep it, the README table and `vim()` in step.
- **Renaming** happens in the clip list (double-click, F2, `r`, or the pencil). Before compressing it sets `Clip::outputName`; afterwards it renames the file on disk through `rename_result`. A renamed clip shows its new name in the list; the stage keeps the source name.
- Judge interface changes by looking: run `npm run dev` and take screenshots in both colour schemes. `?clips` opens the demo clips at startup and `?frame=native` shows Linux's frame, so a headless browser can capture a state without clicking. The built-in browser pane's screenshots crop on a display scaled to 150%; a headless Edge or Chrome at a fixed size works. If a component's styles stop updating in `npm run dev`, restart it: Vite's per-component CSS can go stale. For a phone size, use the DevTools protocol with device emulation (`Emulation.setDeviceMetricsOverride` with `mobile: true`, then `Page.captureScreenshot`): Edge's `--screenshot` lays a 375-pixel window out wider than it crops, so it shows overflow that isn't there.
- The mock planner in `mock.ts` copies the Rust rule for resolution, audio and verdict, for design work without a Rust build; change them together. Lite and the size test use the real planner through WebAssembly (`planner.ts`), and so does `fit.ts`'s retry (`lower_bitrate`, `SIZE_RETRIES`, now in `plan.rs`). ## Verified, and not

Verified on Linux x86-64 with FFmpeg 6.1 and no GPU (before the rename): 56 tests, and the real app launched in both dev and release-style builds, trimmed with a mouse, previewed, and compressed files under the limit.

Verified on Windows 11 with FFmpeg 9.0 and an RTX 5070 Ti laptop GPU: `cargo fmt`, `clippy` and `svelte-check` clean; 98 tests pass (77 unit, 17 e2e, 4 shell; the read-only-folder e2e test runs on Linux only), including NVENC jobs that start on the GPU. The interface was checked on the mock backend at 1180×780 and 900×620 in both schemes. The owner then used the installed app on Windows by hand (15 November 2026, plan 3's "By hand"): Copy then paste into Discord, drag-out, the custom title bar (snap, maximise, a second monitor), Replace the original, renaming a finished file, cancel, quit, Open with, the update from one release to the next, and cutting a result (it starts where the handle is).

E2e tests that check a particular encoder name it in `options.encoder`, and tests that depend on queue order set `parallel_jobs = 1`; a machine with a GPU or many cores otherwise changes what they observe. `a_hardware_encoder_that_misses_hands_over_to_the_cpu` covers the GPU path and skips itself without one.

Windows keeps a killed FFmpeg's output locked for a moment (error 32), so `Cleanup` removes files `patiently`, retrying for up to about five seconds (a CI runner's Defender held one for over a second).

Unverified, so check these first on a new machine:
- Hardware encoder success paths other than NVENC (Quick Sync, AMF, Media Foundation, VAAPI). Their flags are the common FFmpeg settings for each; only fail-and-fall-back has run.
- Linux app runs in an installed build, including preview playback through the loopback server.
